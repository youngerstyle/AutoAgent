# 用户视角真实验收

## 问题

现有 `test:e2e` 使用 Mock Provider，只验证 Mission、Plan 和 Ticket 能否走到终态。它不打开最终产物，也不判断产物是否满足 human 的原始目标。因此，“流程完成”“文件存在”和“模型声称通过”都可能成为假阳性。

## 原则

上线结论必须同时满足三层证据：

1. **Engine 证据**：Agent、Ticket、Mission 的状态和持久化符合契约。
2. **真实团队证据**：使用已配置的真实 Provider 完成一轮 Mission，不使用 Mock。
3. **用户验收证据**：从原始目标推导操作清单，打开最终产物，像用户一样操作并观察结果。

前两层通过、第三层失败时，整体仍然失败。不得用文件数量、模型输出、QA 的静态检查或 `completed` 状态替代用户验收。

## 用户验收规则

- 验收对象是最终产物，不是运行记录。
- 验收清单来自该 Mission 的原始目标和成功标准，不是平台硬编码的通用“完成条件”。
- Web 产物必须在真实浏览器中启动并操作；需要验证核心路径、刷新后的状态、控制台异常和目标视口。
- 游戏必须实际进入可玩状态并验证输入、状态变化、胜负或重开等核心循环；仅检查 Canvas 非空或文件存在不算通过。
- CLI、服务或桌面产物采用对应的真实运行器和用户入口，不能只做静态分析。
- 发现问题时记录“期望、实际、复现步骤、证据”，任务保持未验收，修复后从最终产物重新执行全部相关步骤。

## 自动化边界

仓库提供 `npm run test:acceptance:real` 作为真实环境金丝雀。它使用真实 Provider 创建一个具有明确浏览器验收口径的 Mission，并验证最终产物。

该金丝雀证明平台具备真实交付能力，但不能替代其他 Mission 的领域验收。每次声称某个具体项目可上线前，仍必须针对该项目原始目标执行对应的用户验收；例如待办清单的通过不能证明坦克游戏正确。

## 失败条件

以下任一情况必须让真实验收失败：

- 未配置真实 Provider，或实际使用了 Mock。
- Mission 超时、失败、等待人工输入或存在未完成 Ticket。
- 最终产物缺失、无法启动或打开后空白。
- 原始目标中的核心操作不能完成或结果错误。
- 刷新、持久化、响应式等明确成功标准不成立。
- 页面出现影响功能的脚本错误或未处理异常。

## 报告

真实验收命令输出并保存：

- workspace、task、最终状态和 Ticket 状态；
- 浏览器操作断言；
- 控制台错误；
- 桌面与手机截图；
- 失败时的 snapshot 和复现信息。
